5. FINDINGS (detailed)
----------------------------------------------------------------
  ID:          CA-001
  TITLE:       Mobile Viewport Navigation Overflow
  LENS:        DESIGN
  SEVERITY:    MEDIUM
  CONFIDENCE:  HIGH
  LOCATION:    Primary Navigation Header (all pages)
  REPRO:       1. Resize viewport width to 375px. 
               2. Observe the primary navigation (`nav.primary-nav`).
  EXPECTED:    Navigation wraps into a hamburger menu, or elements adapt to prevent horizontal overflow on standard mobile devices.
  ACTUAL:      The navigation container retains a width of ~453px on a 375px screen (`display: grid`), causing horizontal scrolling/overflow and obscuring the final menu items.
  EVIDENCE:    Extracted DOM properties show `scrollWidth` = 453px inside a 375px viewport.
  HYPOTHESIS:  CSS Grid/Flexbox properties for the header do not include a media query breakpoint to collapse the navigation into a mobile menu toggle.

  ID:          CA-002
  TITLE:       Inconsistent Framework Formatting
  LENS:        DATA
  SEVERITY:    POLISH
  CONFIDENCE:  HIGH
  LOCATION:    Templates (`#/templates`) -> Framework dropdown & Explore Filters
  REPRO:       1. Navigate to Templates (`#/templates`). 
               2. Open the framework/catalog selector dropdown.
  EXPECTED:    All frameworks follow title-casing (e.g., "NIST CSF 2.0", "CMMC 2.0").
  ACTUAL:      MITRE frameworks appear as raw IDs or lowercase strings: `mitre-attack`, `mitre-attack-ics`, `mitre-d3fend`.
  EVIDENCE:    DOM option values and labels directly expose lowercase identifiers rather than formatted display names.
  HYPOTHESIS:  The UI is pulling raw dictionary keys from the data schema for MITRE frameworks without passing them through a display name formatter.

  ID:          CA-003
  TITLE:       Accessibility Tree Exposes Disabled Options Prematurely
  LENS:        USER
  SEVERITY:    LOW
  CONFIDENCE:  MEDIUM
  LOCATION:    Start (`#/start`) -> Questionnaire Dropdowns
  REPRO:       1. Navigate to Start page. 
               2. Inspect "Data sensitivity" combobox options before filling "System type".
  EXPECTED:    The `select` itself should be `disabled`, but its nested `<option>` elements don't inherently need ARIA disabled tags if the parent is locked, or they should correctly update when the parent unlocks.
  ACTUAL:      Natively they are not disabled, but the accessibility tree flags options as `disableable disabled`, which could confuse screen readers as they progressively unlock.
  EVIDENCE:    A11y tree reports options as `disableable disabled` until the first form field triggers React state updates.
  HYPOTHESIS:  React form state or standard progressive disclosure logic is applying attributes inconsistently across parent/child elements during initial render.

  ID:          CA-004
  TITLE:       "Recommended" Playbooks Bypass Search Filters
  LENS:        USER
  SEVERITY:    POLISH
  CONFIDENCE:  HIGH
  LOCATION:    Playbooks (`#/playbooks`)
  REPRO:       1. Navigate to Playbooks (`#/playbooks`). 
               2. Type a very specific search term (e.g., "FedRAMP").
  EXPECTED:    Only playbooks related to FedRAMP appear.
  ACTUAL:      The filtered count says "2 playbooks", but the UI displays 5 playbooks because the "Recommended for new users" block (3 playbooks) remains pinned regardless of the search query.
  EVIDENCE:    `uid=45_3` text reads "2 playbooks", but 5 cards are rendered in the DOM.
  HYPOTHESIS:  Intentional UX decision to keep a fallback visible, but conflicting with the quantitative text string.
