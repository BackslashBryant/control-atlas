7A. COMPETITOR INVENTORY (WHAT THEY OFFER)

---

I-ASSURE (primary comparator — practitioner community standard for free RMF Word artifacts)
- Catalog: 18 NIST 800-53 control-family Word templates (AC, AT, AU, CA, CM, CP, IA, IR,
  MA, MP, PE, PL, PM, PS, RA, SA, SC, SI) plus legacy DIACAP templates.
- Format: .docx (e.g. RMF_Access Control Plan.docx, 1.77 MB; CA family 64 KB).
- Structure: Per-family "Plan" documents mapped to NIST 800-53A assessment procedures;
  individual traceability to assessment procedures stated as design goal.
- Discovery UX: WordPress download table — family name, download count, date, single Download
  button per row. No in-browser preview or configuration.
- Trust signals: "Over 425 ATOs received... never denied by the Approving Authority";
  per-file download counts (12,000–25,000+ per family); SDVOSB certification badge.
- Currency: Last updated June–September 2019 (Rev 4/early Rev 5 era; no visible 2024–2026 refresh).
- Related free tools: Scan Manager (POA&M/RAR from Nessus/SCAP/checklists); STIG-CCI-Control
  Mapper — extends template ecosystem into automation.
- Visual design: Functional contractor-site aesthetic (~2018); not cohesively branded; credible
  to DoD practitioners via social proof counts, not via UI polish.

FEDRAMP.GOV (authoritative cloud ATO package templates)
- Catalog: Full authorization package — SSP, SAP, SAR, Risk Exposure Table, security test case
  workbook, baseline-specific Appendix A templates, POA&M Excel template.
- Format: Word (.docx) and Excel (.xlsx) — required for FedRAMP submission.
- Structure: Prescriptive sections with instructional text per field; baseline-specific appendices;
  aligned to NIST SP 800-53 Rev 5 as of Rev 5 transition.
- Discovery UX: Official .gov document library page; download links; no generator.
- Trust signals: U.S. government official site; mandatory for FedRAMP path.
- Currency: Actively maintained for Rev 5 transition (2024–2026 guidance documents reference
  current templates).
- Visual design: USWDS-style FedRAMP site; plain but authoritative; beats commercial sites on
  trust, not delight.

NIST CSRC — SP 800-18 Rev. 2 (June 2026)
- Catalog: System Security Plan outline example, Privacy Plan outline, C-SCRM Plan outline,
  Roles & Responsibilities — supplemental DOCX downloads.
- Format: Official .docx outlines (not full populated baselines).
- Structure: Defines essential system plan elements correlated to RMF steps; replaces Rev 1 (2006).
- Discovery UX: Publication detail page with supplemental material links.
- Trust signals: Canonical NIST source; June 2026 final — newest official SSP structure guidance.
- Visual design: CSRC standard; reference portal not product UX.

NIST CSRC — RMF Assessment Cases (Word)
- Catalog: One Word file per assessment case per control; 18 zip files by control family.
- Format: .docx inside .zip (e.g. AC family = 22 separate assessment case documents).
- Structure: Deep per-control assessment procedure worksheets — closest official analog to
  I-Assure's per-procedure traceability.
- Discovery UX: Dense CSRC download tables with zip-per-family organization.
- Currency: SP 800-53A Rev 5 era assessment cases.
- Visual design: Reference/download page; not practitioner-friendly discovery.

CIVICACTIONS SSP-TOOLKIT (GitHub — automation-oriented)
- Catalog: SSP front matter, control implementation YAML (OpenControl), appendices; Makefile workflow.
- Format: YAML source → generated Markdown/PDF via compliance-masonry/OSCAL pipeline.
- Structure: Machine-readable controls intended for continuous compliance automation.
- Discovery UX: GitHub README; developer onboarding required.
- Trust signals: CivicActions federal dev shop; GPL/CC0; 52 GitHub stars.
- Visual design: N/A (developer tool); strongest for CI/CD integration, weakest for ISSO self-serve.

CYBERZESHAN GRC FRAMEWORK TOOLKIT (GitHub — narrative markdown)
- Catalog: SSP template, SAP template, step-by-step RMF guide (MIT license).
- Format: Markdown on GitHub.
- Structure: Excellent narrative SSP outline (system ID, FIPS 199, architecture, laws, per-control
  implementation sections with prompts) — but only sample controls written out (AC-1, AC-2, AC-3,
  AC-17, AU-2, etc.), not full baseline enumeration.
- Discovery UX: GitHub repo browse; no generator.

7C. HOW CONTROL ATLAS STACKS UP (HONEST VERDICT)

WHERE CONTROL ATLAS WINS (design and experience)
1. End-to-end product UX — Only Control Atlas connects "I need an SSP" → pick template → configure
   → generate → download inside a cohesive compliance map product. I-Assure and NIST are file pantries;
   FedRAMP is a mandatory forms library. For a practitioner already exploring controls in Control Atlas,
   the template path is dramatically lower friction than leaving to download .docx files.

   CA-WD-022 overlap bug is fixed).

   Worksheet export all ~1,196 NIST 800-53 controls programmatically. That beats cyberzeshan's
   sample-control markdown and matches automation value of CivicActions for row coverage — but
   delivers it through a click instead of a Makefile.

   competitors don't emphasize this (I-Assure downloads; FedRAMP assumes desktop editing).
5. Cross-linking — Playbook "Control Inheritance Model" → Generate Inheritance Worksheet;
   Start Here results → template CTAs. No free competitor offers this workflow integration.

WHERE CONTROL ATLAS LOSES (substance and practitioner expectations)
1. Output format — The largest gap. I-Assure, FedRAMP, and NIST assessment cases all deliver Word
   or Excel. ISSOs, eMASS uploaders, and FedRAMP CSPs live in .docx/.xlsx. Markdown/CSV exports
   read as "developer prototype" to the core GRC audience regardless of UI polish.
2. Document depth and submission readiness — I-Assure's 1.77 MB AC Access Control Plan and per-family
   structure embed 800-53A assessment procedure traceability — the format validators expect. Control
   Atlas Security Plan Starter truncates Inheritance Summary and Evidence Expectations to one control
   row (CA-002) while claiming SSP outline status — a user comparing side-by-side with I-Assure or
   FedRAMP SSP will notice immediately.
3. Stubs vs promises — Five of nine Control Atlas template types are stubs or fixed checklists (CA-004).
   I-Assure's catalog is smaller (18 family plans, not 9 artifact types) but each download is a complete,
   battle-tested document. FedRAMP templates are exhaustive by regulation. Control Atlas over-promises
   on the Templates hub card copy relative to export substance.
4. Trust and authority signals — I-Assure leads with "425 ATOs" and 25,462 downloads on AC alone.
   FedRAMP leads with .gov authority. Control Atlas shows no template version, last-updated date, or
   download/community proof on the Templates surface — design gap for evaluators asking "who else uses this?"
5. Currency — I-Assure templates are stale (2019) but still widely used because format is familiar.
   NIST SP 800-18r2 (June 2026) supersedes 2006 guidance and defines new system plan elements Control
   Atlas templates do not visibly reference. FedRAMP Rev 5 templates are current. Control Atlas data
   build is June 2026 but template *structure* does not mirror newest official SSP outline examples.
6. FedRAMP path — Selecting FedRAMP Rev. 5 framework in Control Atlas yields placeholder output (CA-019).
   FedRAMP.gov provides the real required templates. For cloud SaaS Start Here recommendations pointing
   to FedRAMP baselines, this is a critical competitive failure.

NET DESIGN/POSITIONING READ (for template promotion)
- Control Atlas templates win the "discovery and generation moment" — the UI is 2–3 years ahead of
  I-Assure's download page in product feel.
- Control Atlas templates lose the "attach to authorization package moment" — output format and
  document completeness do not yet compete with I-Assure Word plans or FedRAMP official packages.
- Honest positioning vs I-Assure: "Interactive blank starters tied to the public map" — not
  "replacement for I-Assure RMF templates" or "FedRAMP submission package."
- To stack up visually AND substantively: add .docx export (even if generated from same engine),
  surface build/version date on Templates hub, show exemplar preview before download, fix truncated

8B. LAYOUT & INFORMATION ARCHITECTURE PROBLEMS (WHY IT FEELS BAD)

---

1. INVERTED PRIORITY STACK (critical)
   The visual hierarchy reads: Global nav → Page title → Subtitle → Atlas-only search → three filter
   checkboxes → long instructional paragraph → Map/List tabs → FINALLY the graph → matrix/table/footer.
   The map is buried. For a route named "Atlas" and a nav item permanently highlighted as primary,
   the graph should occupy minimum 60–70% of above-the-fold viewport on desktop, not ~27% width
   and below 50% vertical offset.

2. TRIPLE SEARCH CONFUSION
   Header "Search records and glossary" + "Open search" + Atlas-specific "Search Atlas Map" with
   "Open map" button while already on the map page. Three search affordances compete; "Open map"
   label implies navigation not in-place filter.

3. SIDE TABLE vs GRAPH WIDTH MISMATCH (AC-2 and hierarchy at wide breakpoints)
   At 1920px the connected-item table (~848px) is ~1.6× wider than the graph (~527px). The
   signature visualization is the smaller pane. Practitioners want to see relationships spatially;
   instead they get a wide metadata table and a postage-stamp graph.

4. COVERAGE MATRIX ORPHANED
   Matrix is a third visual system (grid heatmap) below or beside graph without clear sizing rules.
   On hierarchy view it falls below fold; on AC-2 it shares above-the-fold with graph creating
   visual competition. Neither placement feels intentional.

5. AUTO-ZOOM TO UNREADABLE (AC-2)
   Default 0.2x zoom fits twelve nodes as horizontal hairlines — defeats purpose of focused map.
   User must discover zoom controls (7 of them) to make the view usable. First impression: broken.

6. DUPLICATE NODE LABELS
   Every node shows label text twice concatenated (AC-2AC-2, SP 800-53 Rev. 5SP 800-53 Rev. 5).
   Reads as rendering bug; erodes trust in graph accuracy.

7. GENERIC EDGE SEMANTICS
   All edges labeled "leads_to" — visually clutters without semantic value (maps_to, implements,
   assesses, etc. would differentiate relationship types). Looks like placeholder graph.

8. SCROLL-GATED EXPERIENCE
   ~1900px page height means Atlas is a scrolling landing page, not a workspace. Footer (404px tall
   measured) appears after graph+matrix — users hunting for matrix or legend may never scroll.

9. MOBILE IS NON-FUNCTIONAL AS A MAP
   With ~212px header + PageHeader + search + intro, graph is a sliver. Product should default
   to List tab and collapse PageHeader on ≤768px; current Map-default mobile is unusable.

10. ATLAS PULL TAB + NAV REDUNDANCY
    Vertical "ATLAS" tab on every page duplicates nav item already permanently styled as primary CTA.
    Adds visual noise at right edge without clear distinct function.

11. FILTER CHECKBOXES ABOVE GRAPH
    Three "Show..." toggles on hierarchy view consume horizontal space; all default on; practitioner
    value unclear on first visit. Should live in legend drawer or collapsed "Display options."

12. WORDY PANEL INTROS
    Every graph region preceded by h3 + 2-sentence instructional copy + "Diagram ready: N nodes..."
    status line. Compare/Explore surfaces are dense too, but Atlas is the worst offender because
    the copy pushes the actual diagram down.

13. LIST VIEW NOT A CLEAN SWAP
    List mode keeps heavy map chrome; rows are card-stacked not scannable table; duplicate names;
    graph may remain in DOM. List should be full-bleed table below compact toolbar, not nested cards.

14. MAX-WIDTH / LEFT MARGIN DEAD SPACE
    On narrower IDE/panel widths content column hugs left with large empty grid margin — graph feels
    like a widget in a marketing page, not immersive workspace.

15. TAB STATE BUG
    Observed Map tab aria-selected true while List tab active/focused — undermines Map/List toggle trust.

a taste mismatch.
