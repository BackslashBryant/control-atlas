## 3. Ship and deploy — this is direct-push, no PR (established practice)

This repo has never used PRs for this owner's own work (`no-pr` is the
standing practice, not a one-time exception). The deploy mechanism is
GitHub Pages via `.github/workflows/pages.yml`, triggered by a push to
`main`. The repo already has the tooling for this exact situation — use it,
don't hand-roll a push sequence:

1. Finish W2 on this branch (or a continuation branch off it — either is
   fine, history is linear so far and should stay that way).
2. Run the full gate list in §2 above; fix anything red, per `VERIFY.md`'s
   two legal report forms only.
3. Commit locally (small, reviewable commits, same convention as this
   sprint's prior commits — `git log --oneline` on this branch for the
   style to match).
4. Ship with `node tools/ship-to-main.mjs` (unset `GITHUB_TOKEN` first if
   set — the script warns about this). It pushes the branch, waits for the
   "Public Repo Checks" required check via `tools/wait-for-checks.mjs`, then
   fast-forwards local `main` and pushes `origin main` for you. This is the
   established path — do not invent a different push sequence, and do not
   force-push.
5. Confirm the Pages deploy: watch `pages.yml` complete
   (`gh run watch` or `gh run list --workflow=pages.yml`, `env -u
   GITHUB_TOKEN` per this repo's established gh-auth workaround), then load
   the live URL and do a real smoke check — at minimum, the home page, one
   record page (confirm the "Where this sits" rail and relationship-class
   strip from W7 render live), and the new W2 drill-down entry points.
   `pages-live-smoke.yml` may already cover part of this in CI; the agent
   still loads and reads the live site itself — don't only trust the green
   check, and don't hand this step to the owner.
6. Report per the sprint doc's §15 contract: `Verified: <command> ->
   <result>` for everything, `NOTED (not done)` for anything deliberately
   left, no hedged language.
